# YASM — GLTF Implementation Notes

**Тип документа:** Техническое дополнение к `GLTF-Plan.md`  
**Назначение:** Зафиксировать архитектурные нюансы, математические требования и потенциальные ошибки, которые необходимо учитывать при дальнейшей реализации GLTF-подсистемы.

> Этот документ дополняет основной roadmap. Он не заменяет его и не требует повторной реализации уже готовых компонентов.

---

## 1. Общие архитектурные принципы

### 1.1. Разделение Model Data и Runtime State

Необходимо сохранять строгое разделение между загруженной моделью и её runtime-состоянием.

**GltfModel** — общие, неизменяемые данные модели:

- Геометрия и индексы.
- Материалы и текстуры.
- Scene graph.
- Skin definitions.
- Animation clips и keyframes.
- Исходные трансформации узлов.

**Runtime Model Instance** — состояние конкретного экземпляра модели:

- Текущие трансформации узлов.
- Текущая анимация и её время.
- Результаты вычисления глобальных трансформаций.
- Skinning matrices.
- Visibility overrides.

Одна загруженная модель должна использоваться несколькими персонажами одновременно. Изменение позы одного персонажа не должно влиять на остальных.

**Важно:** нельзя хранить текущую позу, время анимации или другие изменяемые данные конкретного персонажа непосредственно в общем `GltfModel`.

### 1.2. Независимость Loader от Renderer

`GltfModelLoader` отвечает только за чтение glTF и преобразование данных в структуры YASM.

Он не должен:

- Создавать GPU buffers.
- Создавать Minecraft render resources.
- Вызывать OpenGL.
- Отправлять draw calls.
- Управлять временем анимации.
- Изменять runtime-позу персонажа.

`YasmModelRenderer`, наоборот, должен работать с уже загруженными данными и runtime-состоянием, не занимаясь разбором исходного glTF.

### 1.3. Математические соглашения

Для всей подсистемы необходимо использовать единые соглашения:

- Порядок умножения матриц.
- Порядок применения трансформаций.
- Представление quaternion.
- Соглашение о расположении элементов матрицы.
- Пространство координат для вершин и нормалей.

Нельзя допускать, чтобы loader, pose evaluator и renderer интерпретировали одну и ту же матрицу по-разному.

Особенно важно документировать, в каком пространстве находятся skinning matrices.

## 2. Skeletal Pose Evaluation

### 2.1. Исходная поза и текущая поза

Runtime pose должна инициализироваться из исходных трансформаций узлов модели.

Нужно различать:

- **Bind pose** — поза, относительно которой были созданы inverse bind matrices.
- **Default pose** — трансформации узлов, заданные в самом glTF.
- **Runtime pose** — трансформации, полученные после применения анимации.

Не следует автоматически считать эти понятия взаимозаменяемыми.

Для сброса анимации необходимо иметь возможность восстановить исходные значения TRS каждого узла.

### 2.2. Сброс позы перед применением анимации

Текущий `SkeletonPose.applyAnimation(animation, time)` применяет значения только к узлам и свойствам, для которых существуют animation channels.

Это создаёт потенциальную проблему.

Например:

1. Анимация A изменяет rotation и translation узла.
2. Затем запускается анимация B, которая изменяет только rotation.
3. Translation остаётся от предыдущей анимации A.

В результате персонаж может получить некорректную позу.

Для первоначальной реализации рекомендуется следующий контракт:

1. Восстановить default pose.
2. Применить все каналы выбранной анимации.
3. Пересчитать локальные и глобальные матрицы.
4. Обновить skinning matrices.

Таким образом, результат вычисления одного кадра не зависит от того, какая анимация выполнялась до него.

Если в будущем появится blending или additive animation, для них можно будет реализовать отдельные правила композиции поз.

### 2.3. Иерархия узлов

Глобальная трансформация дочернего узла должна учитывать трансформации всех его родителей.

Концептуально:

`GlobalTransform(node) = GlobalTransform(parent) * LocalTransform(node)`

Для корневого узла:

`GlobalTransform(root) = LocalTransform(root)`

Порядок пересчёта должен гарантировать, что родитель уже обработан до дочернего узла.

Необходимо учитывать:

- Узлы без родителей.
- Несколько независимых корневых узлов.
- Узлы с matrix вместо TRS.
- Глубокие иерархии.
- Некорректные циклические ссылки.

### 2.4. Matrix Nodes и TRS

glTF node может задавать трансформацию через:

- `translation`, `rotation`, `scale`;
- `matrix`.

Эти варианты нельзя применять одновременно как независимые трансформации.

Если узел использует `matrix`, необходимо сохранить корректную матрицу и не пытаться без необходимости преобразовывать её в TRS.

В частности, произвольная матрица может содержать shear, который нельзя корректно представить обычными translation, rotation и scale.

При применении анимации к узлу с matrix необходимо определить и документировать поведение. Нельзя молча смешивать исходную matrix-трансформацию с анимируемыми TRS.

## 3. Skinning Matrices — критически важный нюанс

### 3.1. Пространство координат

Для GPU skinning недостаточно просто вычислить:

`GlobalJointTransform * InverseBindMatrix`

Эта формула даёт преобразование, которое нужно интерпретировать относительно выбранного пространства координат.

Если вершины передаются в shader в локальном пространстве skinned mesh node, стандартная формула skinning matrix имеет вид:

`SkinMatrix = Inverse(GlobalMeshTransform) * GlobalJointTransform * InverseBindMatrix`

Где:

- `GlobalMeshTransform` — глобальная трансформация узла, содержащего skinned mesh.
- `GlobalJointTransform` — глобальная трансформация соответствующего joint.
- `InverseBindMatrix` — inverse bind matrix из glTF.

Таким образом, skinning matrix зависит не только от skin, но и от конкретного mesh node, использующего этот skin.

### 3.2. Один Skin для нескольких Mesh Nodes

В glTF один skin может использоваться несколькими узлами с mesh.

Если эти узлы имеют разные глобальные трансформации, им могут требоваться разные наборы skinning matrices.

Поэтому API вида:

`skinningMatrices(skinIndex)`

может оказаться недостаточным.

Нужно определить один из вариантов архитектуры:

**Вариант A — матрицы в глобальном пространстве модели**

Хранить:

`GlobalJointTransform * InverseBindMatrix`

Renderer дополнительно учитывает преобразование mesh node и выбранное пространство вершин.

**Вариант B — матрицы относительно конкретного Mesh Node**

Вычислять:

`Inverse(GlobalMeshTransform) * GlobalJointTransform * InverseBindMatrix`

В этом случае результат должен быть привязан к конкретному mesh node и skin.

Для будущего GPU renderer необходимо выбрать один вариант и использовать его последовательно.

**Рекомендация:** решить этот вопрос до реализации GPU skinning. Не стоит фиксировать API, предполагающий один набор матриц на skin, пока не определено пространство координат вершин.

### 3.3. Нормали при Skinning

Нельзя автоматически применять к нормалям ту же операцию, что и к позициям.

Для нормалей необходимо учитывать корректное преобразование направления, включая особенности неравномерного scale.

В простом случае можно использовать преобразование нормали соответствующей матрицей с последующей нормализацией.

Если используется матрица с неравномерным масштабированием, нужно учитывать inverse-transpose соответствующей линейной части матрицы.

Также необходимо нормализовать итоговую нормаль после смешивания влияний joints.

### 3.4. Весовые коэффициенты

Для каждого vertex используются `JOINTS_0` и `WEIGHTS_0`.

Необходимо определить поведение для следующих случаев:

- Сумма весов равна 1.
- Сумма весов отличается от 1 из-за погрешности.
- Сумма весов равна 0.
- Весовые коэффициенты содержат некорректные значения.

Для обычного skinning сумма весов должна быть корректно нормализована либо должна обрабатываться с учётом допустимого формата данных.

Нулевую сумму весов нельзя использовать как делитель. Нужно предусмотреть безопасное поведение, например сохранение исходной позиции вершины.

Необходимо также проверить, что все joint indices действительно принадлежат используемому skin.

## 4. Animation System

### 4.1. Animation Sampler и Animation Controller — разные задачи

`GltfAnimationSampler` отвечает за интерполяцию значений между keyframes.

`AnimationController` отвечает за управление воспроизведением:

- Выбор клипа.
- Текущее время.
- Скорость воспроизведения.
- Looping.
- Pause и resume.
- Stop и restart.
- Определение завершения анимации.

Не следует смешивать эти обязанности.

### 4.2. Интерполяция

Должны сохраняться уже реализованные правила:

| Interpolation | Поведение |
|---|---|
| STEP | Используется предыдущее значение до следующего keyframe |
| LINEAR | Линейная интерполяция |
| Rotation LINEAR | SLERP с shortest-path |
| CUBICSPLINE | Cubic Hermite interpolation |

Необходимо учитывать:

- Время до первого keyframe.
- Время после последнего keyframe.
- Анимацию с одним keyframe.
- Нулевую продолжительность.
- Некорректные или неупорядоченные timestamps.
- Нормализацию quaternion после интерполяции.

Для quaternion нельзя использовать обычную покомпонентную линейную интерполяцию без последующей корректной обработки.

### 4.3. CUBICSPLINE

Для glTF CUBICSPLINE каждый keyframe содержит:

- In tangent.
- Value.
- Out tangent.

При вычислении Hermite interpolation необходимо учитывать длительность интервала между соседними keyframes при масштабировании tangent values.

Нельзя воспринимать tangent как обычное значение keyframe.

### 4.4. Начало и конец клипа

Продолжительность клипа должна определяться по временным данным его samplers.

Нельзя предполагать, что все animation channels имеют одинаковые timestamps или одинаковую длину.

Для loop playback нужно корректно обрабатывать переход от конца клипа к началу.

Для non-looping playback необходимо остановить время на конце клипа и сообщить контроллеру о завершении.

## 5. Visibility System

### 5.1. Независимость уровней видимости

Visibility должна поддерживать независимое управление:

- Весь модельный экземпляр.
- Отдельный node.
- Отдельный material.

Например, скрытие материала должно влиять на все primitives, которые его используют, но не должно менять visibility других материалов.

Скрытие node не должно менять материал или исходную геометрию.

### 5.2. Наследование видимости

Нужно определить поведение дочерних узлов при скрытии родителя.

Рекомендуемое поведение:

- Если node скрыт, его subtree не рендерится.
- Если node показан, это не должно автоматически отменять скрытие его родителя.
- Visibility material применяется независимо от node visibility.
- Visibility model имеет высший приоритет и отключает весь экземпляр.

Итоговая видимость primitive должна вычисляться из всех соответствующих условий, а не храниться как единственный флаг.

### 5.3. Не изменять исходную модель

Скрытие частей модели должно происходить через runtime overrides.

Не следует удалять primitives, менять исходный список nodes или модифицировать общие данные `GltfModel`.

Это особенно важно, когда одна модель используется несколькими персонажами.

## 6. Material и Texture System

### 6.1. Разделение Image, Texture и Material

В glTF это три разных уровня:

- **Image** — источник пиксельных данных.
- **Texture** — ссылка на image и sampler.
- **Material** — описание внешнего вида поверхности и ссылки на текстуры.

Нельзя считать эти объекты одним и тем же ресурсом.

Несколько texture objects могут ссылаться на один image, а несколько материалов — использовать одну texture.

### 6.2. Повторное использование текстур

Необходимо избегать повторной загрузки и GPU upload одного и того же ресурса без необходимости.

Следует разделить:

- Декодированные данные изображения.
- GPU texture resource.
- Ссылки на текстуры со стороны материалов.

Жизненный цикл GPU resources должен контролироваться renderer или отдельным resource manager, но не loader.

### 6.3. Alpha Modes

Необходимо корректно различать три режима:

| Mode | Поведение |
|---|---|
| OPAQUE | Полностью непрозрачный материал |
| MASK | Отбрасывание фрагментов по alpha cutoff |
| BLEND | Прозрачное смешивание |

Для BLEND может потребоваться отдельный render pass и сортировка прозрачной геометрии.

Не стоит пытаться обрабатывать все три режима одинаково.

### 6.4. Sampler Settings

Необходимо учитывать параметры sampler:

- Minification filter.
- Magnification filter.
- Wrap S.
- Wrap T.

Для PS1-style renderer может использоваться nearest-neighbor filtering, но это должно быть осознанным правилом renderer, а не следствием потери sampler data при загрузке.

## 7. Validation и Error Handling

Загрузка некорректной модели не должна приводить к случайным ошибкам далеко от места возникновения проблемы.

Нужно проверять входные данные на границе loader.

### 7.1. Scene Graph

Проверять:

- Допустимость индексов nodes.
- Отсутствие циклов.
- Отсутствие противоречивых parent-child связей.
- Корректность ссылок на meshes и skins.
- Корректность default scene.

### 7.2. Accessors и Geometry

Проверять:

- Совместимость component type и accessor type.
- Корректность byte offsets и byte strides.
- Доступность данных в пределах buffer.
- Корректность количества элементов.
- Корректность индексов вершин.
- Конечность числовых значений.

Для FLOAT значений важно проверять не только входное значение, но и результат преобразований, если они могут привести к overflow.

### 7.3. Quaternion и Transform

Проверять:

- Конечность всех компонентов.
- Корректность quaternion.
- Отсутствие некорректного нулевого quaternion.
- Допустимость матриц.
- Корректность значений scale.

Quaternion, полученные из glTF, должны обрабатываться согласованно. Нормализация должна выполняться в определённом месте pipeline, а не случайно в нескольких компонентах.

### 7.4. Materials

Проверять допустимые значения alpha cutoff и других ограниченных параметров.

Если свойство отсутствует, использовать соответствующее значение по умолчанию glTF.

Нельзя молча принимать произвольные значения там, где спецификация задаёт диапазон.

### 7.5. Numeric Conversion

При преобразовании `double` в `float` необходимо учитывать возможность потери конечности значения.

Например, конечное значение `double` может превратиться в бесконечность при приведении к `float`.

Для матриц и vertex data это может привести к труднообнаружимым ошибкам рендеринга.

## 8. Testing Requirements

Документированные smoke tests полезны, но желательно сохранять проверяемые тесты непосредственно в репозитории.

В дальнейшем рекомендуется перенести проверки в автоматизированные тесты или отдельный воспроизводимый developer test harness.

### 8.1. SkeletonPose Tests

Обязательные сценарии:

- Один root node.
- Несколько независимых root nodes.
- Простая цепочка parent-child.
- Глубокая иерархия.
- Вращение родителя.
- Перемещение родителя.
- Matrix-based node.
- Сброс к default pose.
- Несколько независимых экземпляров одной модели.

### 8.2. Skinning Tests

Особенно важны следующие сценарии:

1. Один mesh node и один skin.
2. Несколько joints в иерархии.
3. Mesh node с собственной трансформацией.
4. Один skin, используемый несколькими mesh nodes.
5. Разные трансформации этих mesh nodes.
6. Вершина с несколькими влияющими joints.
7. Вершина с нулевой суммой весов.
8. Проверка нормалей после skinning.

Проверки должны использовать простые заранее рассчитанные матрицы, чтобы ожидаемый результат можно было проверить без визуального рендеринга.

### 8.3. Animation Tests

Проверять:

- STEP.
- LINEAR.
- SLERP.
- CUBICSPLINE.
- Quaternion shortest path.
- Время до первого keyframe.
- Время после последнего keyframe.
- Переключение между клипами.
- Повторный запуск клипа.
- Loop playback.
- Non-looping playback.
- Сброс pose перед применением нового клипа.

### 8.4. Visibility Tests

Проверять:

- Hide/show model.
- Hide/show node.
- Hide/show parent node.
- Hide/show material.
- Одновременное скрытие node и material.
- Независимость overrides между экземплярами модели.

### 8.5. Reproducibility

Результаты smoke tests должны быть воспроизводимыми.

Желательно сохранять:

- Название теста.
- Входные данные.
- Ожидаемый результат.
- Фактический результат.
- Способ запуска.

Одной записи о том, что тест был успешно выполнен, недостаточно для долгосрочной регрессии.

## 9. GPU Renderer

### 9.1. Разделение ресурсов

Renderer должен управлять GPU resources отдельно от model data.

К GPU resources относятся:

- Vertex buffers.
- Index buffers.
- Vertex array objects или их аналоги.
- GPU textures.
- Shader programs.
- Animation buffers, если они используются.

Загруженная модель не должна напрямую зависеть от времени жизни конкретного GPU context.

### 9.2. Несколько Primitives

Один mesh может содержать несколько primitives.

Каждый primitive может иметь:

- Собственную геометрию.
- Собственный material index.
- Собственный набор индексов.
- Собственные параметры отрисовки.

Renderer должен проходить по primitives и применять соответствующий material и visibility.

Нельзя предполагать, что один mesh всегда соответствует одному draw call или одному материалу.

### 9.3. Unskinned Geometry

Не вся геометрия обязана использовать skinning.

Renderer должен поддерживать обычные primitives без skin.

Наличие skin в модели не означает, что каждая вершина или каждый mesh node обязательно должны деформироваться скелетом.

### 9.4. PS1-Style Rendering

Специфические эффекты PS1-style rendering должны оставаться отдельными настройками renderer.

Например:

- Nearest-neighbor filtering.
- Affine texture mapping.
- Ограниченная точность координат.
- Особенности интерполяции.
- Раздельные opaque и transparent passes.

Не нужно добавлять эти особенности в glTF loader или менять исходные данные модели ради визуального стиля.

## 10. Что не нужно реализовывать

В соответствии с текущими требованиями проекта не следует добавлять без отдельной необходимости:

- Shape Keys.
- Morph Targets.
- Facial Blend Shapes.
- PBR rendering.
- Metallic/Roughness workflow.
- Normal Mapping.
- Ambient Occlusion.
- Emissive Mapping.
- Environment Mapping.
- Сложные animation state machines.
- Blend Trees.
- Многослойное смешивание анимаций.
- Продвинутый cross-fading.
- GLB support как обязательную функцию.

Не следует усложнять первоначальную реализацию функциями, которые не нужны для текущей задачи.

## 12. Критические решения перед GPU Skinning

Перед началом реализации GPU skinning необходимо получить однозначные ответы на следующие вопросы:

- В каком пространстве хранятся позиции вершин?
- В каком пространстве renderer ожидает skinning matrices?
- Учитывается ли `GlobalMeshTransform` при вычислении skinning matrices?
- Может ли один skin использоваться несколькими mesh nodes?
- Как обрабатываются нулевые веса?
- Как преобразуются нормали?
- Где выполняется нормализация весов?
- Как обрабатываются unskinned primitives?

Эти решения должны быть отражены в API и комментариях к соответствующим методам.

**Главный принцип:** не начинать GPU skinning, пока математический контракт между `SkeletonPose` и `YasmModelRenderer` не определён. Иначе есть риск получить визуально работающий частный случай, который сломается на моделях с трансформированными mesh nodes или повторно используемыми skins.
